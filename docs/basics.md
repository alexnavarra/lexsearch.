## 0. Какую задачу мы решаем

Ты готовишься к техническому собеседованию. У тебя есть сотни страниц материалов: документация Rails и PostgreSQL, книги, свои конспекты. Ты спрашиваешь:

> «Как избежать лишних запросов к базе при загрузке связей?»

В Rails Guides нет такой фразы. Там написано «Eager Loading Associations» и «N+1 queries problem», причём по-английски.

**Обычный поиск** (`LIKE '%запрос%'`, Ctrl+F) ищет совпадение **букв**. Здесь он ничего не найдёт: слова другие, и язык другой.

Нам нужен поиск по **смыслу**: найти фрагменты, которые *означают* то же, что и вопрос, даже если слова не совпадают.
Потом эти фрагменты надо отдать LLM (Claude), чтобы она сформулировала ответ своими словами и сослалась на источник.

А раз это подготовка к собеседованию, есть и третья задача: **проверить тебя**. Приложение по тем же фрагментам задаёт вопросы, а Claude сверяет твой ответ с источником.

Всё, что дальше, это детали решения этих задач:

```
1. Найти нужные куски текста по смыслу      → embeddings, Ollama, pgvector, полнотекстовый поиск
2. Ответить на вопрос по найденным кускам   → LLM (Claude), промпт, цитаты
                                           = RAG
3. Задать вопрос и оценить твой ответ       → structured output, LLM в роли проверяющего
```

## 1. Embedding: текст → числа

### Идея в одном предложении

**Embedding** (эмбеддинг, «векторное представление») — это список чисел, в котором модель закодировала **смысл** текста.

```
"как ускорить фильтрацию по json-полю"  →  [0.021, -0.113, 0.540, ..., 0.007]   (768 чисел)
```

### Аналогия: координаты на карте

Представь карту, где каждый текст это точка. Модель расставляет точки так, чтобы **тексты с похожим смыслом оказались рядом**:

```
              ▲  «про базы данных»
              │
              │   • "GIN index on jsonb"
              │  • "ускорить поиск по json-полю"
              │
              │
              │                          • "рецепт борща"
              └────────────────────────────────────────▶  «про еду»
```

На бумажной карте 2 координаты (x, y). У настоящих моделей их сотни или тысячи (у нашей 768). Представить 768-мерное пространство нельзя, но логика та же: **близко = похоже по смыслу**.

Важно: отдельное число в векторе **ничего не означает** само по себе. Нет «числа №5 = про еду». Смысл несёт только **взаимное расположение** векторов.

### Как измерить «близко»

Чаще всего меряют **угол** между векторами (стрелками из начала координат):

- стрелки смотрят в одну сторону → тексты похожи;
- стрелки под прямым углом → тексты не связаны.

Это **косинусное сходство** (cosine similarity): от 1 (одинаковое направление) до 0 (не связаны).
В базе обычно используют **косинусное расстояние** = `1 − сходство`. Чем меньше, тем ближе по смыслу.

Реальные замеры на модели `nomic-embed-text`, которая сейчас стоит в Docker:

| Вопрос «how to make filtering by a json field faster» против... | Сходство | Расстояние |
| --- | --- | --- |
| «A GIN index speeds up containment queries (@>) on jsonb columns» | 0.64 | 0.36 → ближе |
| «A B-tree index supports equality and range queries on sortable data» | 0.52 | 0.48 |
| «Borscht is a sour soup made with beetroot» | 0.43 | 0.57 → дальше |

Обрати внимание: даже совсем не связанный текст не даёт 0. У каждой модели своя «шкала», поэтому абсолютное значение мало что говорит. Важен **порядок**: какой фрагмент ближе остальных.

А теперь тот же вопрос по-русски, «как ускорить фильтрацию по json-полю»: 0.56 / 0.51 / 0.49. Порядок сохранился, но правильный фрагмент почти не отличается от борща. `nomic-embed-text` в основном английская модель. Нам нужны русские вопросы к английским текстам, поэтому на этапе 3 мы перейдём на мультиязычную `bge-m3` (1024 числа) и повторим этот замер.

### Откуда берутся векторы

Их считает **embedding-модель**. Это нейросеть, обученная на огромном количестве текстов так, чтобы похожие по смыслу тексты получали близкие векторы.

**Embedding-модель ≠ чат-модель (LLM).**

| | Embedding-модель | LLM (Claude) |
| --- | --- | --- |
| На входе | текст | текст (вопрос, инструкция) |
| На выходе | **вектор** чисел | **текст** (ответ) |
| Зачем | поиск, сравнение, кластеризация | понимать, рассуждать, писать |
| Скорость/цена | быстро, дёшево | медленнее, дороже |
| Пример | `nomic-embed-text`, Voyage, OpenAI embeddings | Claude Haiku/Sonnet/Opus |

У Claude нет режима «верни вектор», поэтому мы берём отдельную embedding-модель.

### Три правила, которые нельзя нарушать

1. **Одна модель для всего.** Документы и запросы кодируются **одной и той же** моделью. Векторы разных моделей как координаты на разных картах: сравнивать их бессмысленно. Сменил модель, значит, пересчитай все векторы.
2. **Фиксированная длина.** Модель всегда выдаёт векторы одной длины (`nomic-embed-text` 768, `bge-m3` 1024). Колонка в БД объявляется под эту длину.
3. **Слишком длинный текст плохо кодируется.** Вектор один на весь текст. Если засунуть в него целую главу книги, смысл «размажется». Поэтому документы режут на **чанки** (куски по одному разделу или нескольким абзацам), и у каждого чанка свой вектор.

## 2. Ollama: модели у тебя на компьютере

**Ollama** — это программа, которая скачивает open-source модели и запускает их **локально**, отдавая наружу простой HTTP API.

Зачем она нам:

- бесплатно: не нужен ключ и не нужно платить за каждый запрос;
- работает офлайн;
- для обучения качества хватает с запасом.

### Как это устроено у нас

```
┌──────────── твой компьютер ─────────────┐
│                                         │
│  Rails-приложение                       │
│      │  HTTP POST localhost:11434       │
│      ▼                                  │
│  Docker-контейнер "ollama"              │
│      └─ модель nomic-embed-text         │
│         (≈270 МБ, лежит в volume)       │
└─────────────────────────────────────────┘
```

- Контейнер описан в `docker-compose.yml` (сервис `ollama`).
- Модель скачивается один раз командой `ollama pull nomic-embed-text` (её делает `bin/setup`).
- `nomic-embed-text` — embedding-модель: на входе текст, на выходе 768 чисел. Ollama умеет запускать и чат-модели (Llama, Qwen), но нам для чата нужен Claude.
- На этапе 3 добавим `bge-m3` (≈1.2 ГБ, 1024 числа, понимает русский и английский). Префиксы ей не нужны.

### Как к ней обратиться

```bash
curl localhost:11434/api/embed -d '{
  "model": "nomic-embed-text",
  "input": ["search_query: how to make filtering by a json field faster"]
}'
# → {"embeddings": [[0.0556, 0.0110, -0.1372, ...]]}   768 чисел
```

- `input` — **массив**: можно отправить сразу много текстов (батч). Это намного быстрее, чем по одному.
- Префиксы `search_query:` и `search_document:` — особенность модели nomic. Она обучена различать «это вопрос пользователя» и «это фрагмент документа», и с префиксами поиск работает лучше. Правило простое: чанки кодируем с `search_document:`, вопрос с `search_query:`.

В Rails мы обернём этот вызов в сервис `Embeddings` (этап 3), чтобы остальной код не знал, Ollama там или другой провайдер.

## 3. Где хранить векторы: pgvector

### Проблема

У нас 300 чанков, у каждого 768 чисел. Пришёл вопрос, мы посчитали его вектор. Теперь нужно найти **10 чанков, чьи векторы ближе всего к вектору вопроса**. Это называется **поиск ближайших соседей** (nearest neighbors).

Можно хранить векторы в отдельной «векторной БД» (Pinecone, Qdrant, Weaviate). Но тогда данные лежат в двух местах и их надо синхронизировать.

### Решение: pgvector

**pgvector** — расширение для PostgreSQL, которое добавляет:

1. **Тип колонки `vector(N)`**: массив из N чисел.
2. **Операторы расстояния** между векторами.
3. **Индексы** для быстрого поиска соседей.

Векторы лежат в той же таблице, что и текст, тема и источник. Фильтры пишутся обычным SQL.

```sql
-- таблица
CREATE TABLE chunks (
  id        bigserial PRIMARY KEY,
  content   text,
  topic     text,
  embedding vector(1024)
);

-- 5 ближайших по смыслу чанков по теме PostgreSQL
SELECT id, content, embedding <=> '[0.05, 0.01, ...]' AS distance
FROM chunks
WHERE topic = 'postgresql'
ORDER BY embedding <=> '[0.05, 0.01, ...]'
LIMIT 5;
```

Операторы:

| Оператор | Что считает | Наш случай |
| --- | --- | --- |
| `<=>` | косинусное расстояние | **используем** |
| `<->` | обычное (евклидово) расстояние | |
| `<#>` | скалярное произведение (со знаком минус) | |

Мы используем Docker-образ `pgvector/pgvector:pg17`: это обычный Postgres 17, в котором расширение уже собрано. Включаем его миграцией `enable_extension "vector"` (уже сделано на этапе 0).

### Индекс: зачем и какой

Без индекса Postgres сравнивает вопрос с **каждой** строкой (полный перебор). На тысячах строк это миллисекунды и 100% точности. На миллионах строк это медленно.

Векторный индекс (**HNSW**) строит граф «кто чей сосед» и при поиске идёт по графу, а не по всем строкам. Это быстро, но **приблизительно**: изредка он может пропустить настоящего соседа. У нас данных мало, индекс мы делаем, чтобы научиться с ним работать (и увидеть его подвохи на этапе 3).

### gem neighbor

Gem `neighbor` даёт ActiveRecord-обёртку, чтобы не писать SQL руками:

```ruby
class Chunk < ApplicationRecord
  has_neighbors :embedding
end

Chunk.where(topic: "postgresql")
     .nearest_neighbors(:embedding, query_vector, distance: "cosine")
     .first(5)
# у каждого результата есть .neighbor_distance
```

Под капотом это тот же `ORDER BY embedding <=> ... LIMIT 5`.

## 4. Полнотекстовый поиск: когда важны точные слова

Векторный поиск отлично ловит смысл, но плохо ловит **точные** вещи: «VACUUM FULL», «N+1», имя метода `find_each`, название гема. Для модели «VACUUM» и «ANALYZE» почти одинаковы по смыслу: оба «про обслуживание базы».

Для этого в Postgres есть встроенный **полнотекстовый поиск**:

- **`tsvector`**: текст, разобранный на нормализованные слова. Стоп-слова («the», «and», «be») выброшены, слова приведены к основе (stored, storing → `store`).
- **`tsquery`**: запрос в той же форме.
- **`@@`**: оператор «совпадает ли».
- **GIN-индекс**: работает как предметный указатель в конце книги (слово → номера строк).

```sql
SELECT to_tsvector('english', 'Indexes are stored separately from the table data');
-- 'data':8 'index':1 'separ':4 'store':3 'tabl':7
```

Это умнее `LIKE`, потому что учитывает словоформы и ранжирует результаты, но это **не смысл**: «блокировка» и «lock» для него разные слова. Словарь стемминга у каждого языка свой (`'english'`, `'russian'`), поэтому у нас язык хранится в каждом чанке.

## 5. Гибридный поиск: лучшее из двух

| Запрос | Векторный | Полнотекстовый |
| --- | --- | --- |
| «как ускорить фильтрацию по json-полю» | ✅ найдёт GIN index on jsonb | ❌ слова и язык другие |
| «VACUUM FULL» | 🤷 что-то «про обслуживание БД» | ✅ точно |

Поэтому запускаем **оба** поиска и склеиваем результаты. Склеивать по оценкам нельзя: у них разные шкалы (расстояние 0–2 против рейтинга 0.03–1.7). Склеиваем по **местам** в списках методом **RRF** (Reciprocal Rank Fusion): чанк, который оба метода поставили высоко, побеждает. Формула и пример расчёта в `theory.md`, раздел 4.

## 6. LLM и Claude API

**LLM** (Large Language Model) — модель, которая по входному тексту генерирует продолжение: ответ, JSON, резюме. Claude это LLM от Anthropic.

Мы обращаемся к Claude по HTTP через официальный gem `anthropic`:

```ruby
client.messages.create(
  model: "claude-haiku-5-5",
  max_tokens: 1024,
  system: "Ты помогаешь готовиться к техническому собеседованию.",   # правила поведения
  messages: [{ role: "user", content: "Что такое проблема N+1?" }]
)
```

Термины, которые будут встречаться:

| Термин | Что это |
| --- | --- |
| **Токен** | кусок слова, единица счёта текста для модели. Примерно 1 токен ≈ 4 символа английского текста. Цена и лимиты считаются в токенах. |
| **Контекст** | всё, что модель «видит» за один вызов: системный промпт, вопрос, вставленные фрагменты. |
| **System prompt** | инструкции для модели: роль, правила, формат ответа. |
| **Temperature** | «креативность». 0 значит максимально предсказуемо (для извлечения данных), выше значит разнообразнее. |
| **Галлюцинация** | модель уверенно выдумывает факт. Главный враг, с которым борется RAG. |
| **Tool use / structured output** | способ заставить модель вернуть не свободный текст, а JSON по заданной схеме. |

Чем LLM отличается от обычного API:

- **медленная**: секунды, а не миллисекунды → вызываем из фоновых jobs;
- **платная**: каждый вызов стоит денег → логируем токены;
- **недетерминированная**: на один и тот же вопрос может ответить по-разному → валидируем ответ;
- **может ошибаться** → проверяем цитаты, меряем качество.

## 7. RAG: собираем всё вместе

**RAG** (Retrieval-Augmented Generation) = «генерация, дополненная поиском».

Без RAG модель отвечает **по памяти**: что выучила при обучении, то и скажет. Она не знает твоих конспектов, может перепутать версии Rails и может выдумать. И её ответ нельзя проверить по ссылке.
С RAG модель работает как **читатель**: мы сами находим нужные фрагменты, кладём их в промпт и требуем отвечать **только по ним** со ссылками.

Аналогия: экзамен с закрытой книгой против экзамена с открытой книгой, где тебе ещё и закладки на нужных страницах поставили.

### Два конвейера

```
ОФЛАЙН (один раз на документ, в фоне)
  документ ──► режем на чанки ──► считаем embeddings (Ollama) ──► сохраняем в Postgres
                                                                 (vector + tsvector)

ОНЛАЙН (на каждый вопрос)
  вопрос ──► embedding вопроса ──► гибридный поиск в Postgres ──► топ-6 чанков
         ──► промпт: «вот источники [S1]..[S6], ответь только по ним»
         ──► Claude ──► ответ с цитатами [S2] ──► проверяем, что цитаты настоящие

ЭКЗАМЕН (поверх тех же чанков)
  чанк ──► Claude генерирует карточку (вопрос + эталон) ──► ты отвечаешь
       ──► Claude сверяет ответ с источником ──► оценка 0–5 ──► когда показать снова
```

### Главная мысль

**Качество ответа ограничено качеством поиска.** Если поиск не нашёл нужный фрагмент, Claude либо скажет «не найдено» (хорошо), либо начнёт отвечать по памяти (плохо). Поэтому в плане сначала идут этапы поиска (2–5), а LLM только потом (6–8). И поэтому на этапе 9 мы отдельно меряем, насколько хорошо работает поиск (recall@k).

## 9. Потрогай руками (уже работает)

Контейнеры должны быть запущены: `docker compose up -d`.

**1. Посмотри на настоящий вектор:**
```bash
curl -s localhost:11434/api/embed -d '{"model":"nomic-embed-text","input":["hello"]}' | head -c 300
```

**2. Сравни смысл трёх фраз в `bin/rails console`:**
```ruby
require "net/http"

def embed(text)
  res = Net::HTTP.post(URI("http://localhost:11434/api/embed"),
                       { model: "nomic-embed-text", input: [text] }.to_json,
                       "Content-Type" => "application/json")
  JSON.parse(res.body)["embeddings"][0]
end

def cosine(a, b)
  dot = a.zip(b).sum { |x, y| x * y }
  dot / (Math.sqrt(a.sum { _1**2 }) * Math.sqrt(b.sum { _1**2 }))
end

q  = embed("search_query: how to make filtering by a json field faster")
ru = embed("search_query: как ускорить фильтрацию по json-полю")
a  = embed("search_document: A GIN index speeds up containment queries (@>) on jsonb columns")
b  = embed("search_document: Borscht is a sour soup made with beetroot")

cosine(q, a)   # больше
cosine(q, b)   # меньше
cosine(ru, a) - cosine(ru, b)  # отрыв по-русски заметно меньше
```
Общих слов у вопроса и фразы `a` почти нет, а сходство выше. Это и есть поиск по смыслу. А маленький отрыв у русского вопроса показывает, зачем нам мультиязычная модель.

**3. То же расстояние, но силами Postgres:**
```ruby
ActiveRecord::Base.connection.select_value(
  "SELECT '#{q}'::vector <=> '#{a}'::vector"
)  # ≈ 1 - cosine(q, a)
```

**4. Полнотекстовый поиск без всяких таблиц:**
```ruby
ActiveRecord::Base.connection.select_value(
  "SELECT to_tsvector('english', 'Indexes are stored separately from the table data')"
)
# и по-русски: to_tsvector('russian', 'Индексы хранятся отдельно от данных таблицы')
```

## 10. Словарь

| Термин | Коротко |
| --- | --- |
| Embedding / вектор | список чисел, кодирующий смысл текста |
| Размерность | длина вектора (`nomic-embed-text` 768, `bge-m3` 1024) |
| Косинусное расстояние | мера «непохожести» векторов, 0 = одинаковые по смыслу |
| Embedding-модель | нейросеть «текст → вектор» (`nomic-embed-text`, `bge-m3`) |
| Мультиязычная модель | embedding-модель, которая кладёт тексты на разных языках в одно пространство |
| Ollama | программа для локального запуска моделей с HTTP API |
| pgvector | расширение Postgres: тип `vector`, операторы, индексы |
| `neighbor` | Ruby gem для pgvector в ActiveRecord |
| Nearest neighbors | поиск ближайших векторов |
| HNSW | быстрый приблизительный векторный индекс |
| Чанк | кусок документа (раздел, несколько абзацев) со своим вектором |
| tsvector / tsquery | нормализованные слова документа / запроса для полнотекстового поиска |
| GIN | индекс для полнотекстового поиска |
| RRF | способ объединить несколько ранжированных списков |
| LLM | языковая модель, генерирующая текст (Claude) |
| Токен | единица текста для LLM, по ней считается цена |
| Промпт | всё, что мы отправляем модели |
| Галлюцинация | уверенная выдумка модели |
| RAG | найти фрагменты → дать модели → ответ только по ним |
| Recall@k | доля вопросов, где нужный фрагмент попал в топ-k поиска |
| Карточка | вопрос + эталонный ответ, сгенерированные по чанку |
| LLM-as-judge | LLM оценивает ответ по рубрике и источнику |
| Интервальное повторение | показывать карточку тем реже, чем лучше ты её знаешь (SM-2) |
