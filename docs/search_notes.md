# Search notes

Сравнение трёх методов поиска на реальных данных (13 документов, 404 чанка, `bge-m3`).
Hybrid: RRF, k = 60, по 40 кандидатов от каждого метода. Варианты на Ruby и SQL дали одинаковый порядок на всех запросах.
В колонке Hybrid «v2 f1» означает: 2-е место у вектора, 1-е у полнотекстового поиска.

## Наблюдения

- **Полнотекстовый поиск требует все слова.** `websearch_to_tsquery` соединяет слова через AND, поэтому вопрос на естественном языке («уровни изоляции транзакций») часто не находит ничего: в одном чанке нет всех слов сразу. Улучшение: для гибрида строить OR-запрос (`|`) и полагаться на ранжирование.
- **Идентификаторы ломаются парсером.** `has_many` превращается в `'mani'`, `N+1` в `'n' & '1'`. Для кода нужен `simple`-словарь или отдельная колонка.
- **RRF поднимает то, что нашли оба метода, даже если это не лучший ответ.** На запросе про eager loading наши конспекты (`theory.md`, `basics.md`) цитируют этот же вопрос дословно, поэтому их находят оба метода, и они обгоняют настоящий раздел Rails Guides. Помогает фильтр «тип: docs».
- **Учебные заметки загрязняют выдачу.** `theory.md` и `basics.md` пересказывают почти все темы и содержат примеры запросов. Для честной оценки (этап 9) их стоит исключать фильтром.
- **Оценки разных методов несравнимы:** distance 0.3–0.5 и rank 0.1–10 живут в разных шкалах. Поэтому RRF смотрит только на места.
